# 源侧版本行锁与跨库状态写入探针

状态：**真实 MySQL 组件实验通过；没有接入 guardian 或生产恢复许可。** 使用独立源和状态 MySQL 9.5.0。测试使用源控制表 INSERT 触发器递增版本行，并在另一台状态实例写入测试行；[结果](result.json)、[运行日志](runner.log)、[探针源码摘要](probe.sha256)。

| 固定步骤 | 观察 |
| --- | --- |
| 旧写事务已更新版本但未提交 | 普通读看到版本 0；另一事务的 `SELECT ... FOR UPDATE` 等待并以 MySQL 1205 超时 |
| 旧事务提交后 | 获得锁并读取到版本 1 |
| 检查方保持版本行锁 | 新控制写事务更新版本行时以 1205 超时；测试状态库可写入版本 1 |
| 检查方提交并释放锁 | 新控制写事务提交，源版本变为 2，测试状态行仍为 1 |

这表明在本实验前提下，版本锁能阻止已经进入触发器的未提交写和锁持有期间的新写；也说明**状态行写入后释放锁并不保证版本永不变化**。这不是跨库原子提交；锁连接中断、状态库提交结果未知、锁释放后恢复许可被使用、旧事务未进入受控版本行、触发器缺失或被绕过、DDL 以及源实例切换都未验证。

实验未使用真实 guardian、Actor Journal、D、Sink 或生产恢复许可；不能称为端到端恢复。源和状态的 UUID 见结果，实验实例关停前后的状态见 [cleanup-lab.json](cleanup-lab.json)。
