# 整体审查与修正归属

独立审查只读检查基线 b24762f 上的全部生产差异、新调度包、API、SQL、测试及指南；审查本身没有运行实验。作者据此在同一修正轮补测试与修复，实际命令日志另存证据包。没有进行提交、推送或生产部署。

1. **明确失败占住本地名额**：SQL 配额归还后实体未退出，DeathWatch 不释放 attached 名额。局部实际 RED 后，已确认释放的失败实体通过 Shard 让出；释放未知继续保留。GREEN 检查连续三个失败（节点上限为二）后健康任务仍完成。
2. **定义修订分叉**：完成 revision1 后 SQL 接受 revision2，Actor 却拒绝已有 Journal 定义。局部实际 RED 后，仅在原 execution 结束且修订严格增加时持久化新定义，再开始新 execution。旧受管 Define 更新（含改成其他类型）明确拒绝；初始 Define 先登记索引。Supervisor 及 Actor 两层覆盖旧入口，避免 J 先成功而索引冲突。局部 GREEN 不等于跨库原子事务；对应失败须用原身份重试。
3. **bind COMMIT 回复丢失**：MySQL 实际提交 owner 绑定后，测试代理抛出连接异常，本地 owned 映射未登记，导致 running 配额滞留。真实 RED 保留；修复重读准确的 grant/execution/definition/local owner，确认后继续。不能确认时保留释放 fence，不凭异常重试新 Reader。
4. **Cron 冷实体激活边界**：旧 Cron 仍先发实体命令，再由 Actor 进入准入。它不承担 70 万冷任务目录，不承诺同样的冷 Actor 激活上限；保留原触发身份与水位。新的持久化 POST/游标分页是本轮大目录入口。所有受管连接器 IO 仍经同一授权门，但这不构成 70 万个 Cron 的容量证明。

独立审查前还实际发现并修正：跨轮询累积 HELD、旧请求在后续运行完成后被重新执行、不同策略协调器共同准入、Actor 恢复消息覆盖活动 attempt、归还 COMMIT 回复丢失后本地旧授权残留，以及 remember-entities 开启时直接停止导致重新激活。各 RED/GREEN 日志和对应旧源码/冻结字节码分别保存，不把编译接线失败算作协议实验。

最终多表重跑还暴露测试设施竞争：进程全局 close 开关被另一表抢走，CLOSE_UNKNOWN-678c996e4548 的 table-01 被隔离而非预定 table-00，其余 15 表完成。修复仅将 close 探针绑定到指定目标批次，保留失败原始记录，再单独复跑该场景。没有因此更改生产恢复协议。

完整后端首次 527 项中一个旧测试观察异步 stream termination 回调过早；改为等待实际 observer 计数，生产取消/恢复协议没有改变。该失败日志和后续完整测试日志均保留。

原单表真实回归另发现生产兼容性回归：确认失败后的 stopAfter 条件未限定受管任务，使未启用调度的旧 Split 暂停 owner 提前退出，5项原应保留暂停状态的场景失败。失败运行、原始日志和冻结源码保留。修正只给启用跨表准入的任务执行失败后让出；新增旧分支 owner 保留断言，并在相同静态数据集重跑完整22项。该回归不应被归为测试设施故障。

最后自审还固定复现了调度结果重叠：挂起旧 READY 的已提交回复，在另一线程领取并绑定同 execution 的下一窗口，旧本地 owned 条目使新绑定先提交 RUNNING、再抛异常。局部 RED 保存；修复在绑定前检查不同本地旧授权，先返回 defer，不推进新 RUNNING。旧结果经重读确认后才能接续。真实 RELEASE_REPLY_HELD 在其余15表完成后固定该窗口，观察到旧回复返回前新窗口已有 T，最终逐字段收敛，未把旧调用返回当唯一确认途径。

原 CDC 回归的两次共享实例运行在初始化阶段出现超时。原始日志显示 Debezium 在180秒窗口内仍加载数千条 Schema 历史，目标仍为空，尚未到目标故障注入。另发现两轮复用固定复制 serverId741819，属并行设施风险，未取得其导致本次超时的直接证据。保留全部超时、未完成运行和数据库，停止本任务的两棵 CDC 进程树，使用相同 MySQL 镜像/命令的新隔离实例串行重跑最终矩阵，没有修改生产恢复协议、测试断言或 Schema 历史策略。新实例与串行运行同时改变了环境，不能由成功单独归因于其中一项。
