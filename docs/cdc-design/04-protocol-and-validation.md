# 四：把实验变成协议约束，下一阶段应该怎样设计

第三篇已经复现了一个具体问题：同一段源事件恢复后重新分批，当前 batchId 与目标账本不能协调，作业停止。因此下一阶段的首要工作是定义可重放的身份和进度协议，然后才扩大到共享读取器、并行快照和海量表。

本篇全部新增机制均是**设计提案**。文中的状态、身份和验证矩阵没有写入生产代码，也没有通过实现后的端到端验收。当前事实以[源码基线](README.md)与[真实实验](03-real-mysql-journal-failure.md)为准。

## 1. 保留基础设施，调整身份与进度契约

现有项目不需要整体推倒。真正需要改的是：哪些信息可跨恢复稳定识别业务事件，哪些信息仅属于本次传输，以及如何协调目标事实与 Actor 进度。

| 当前组件 | 可以保留的部分 | 需要设计或调整的部分 |
|---|---|---|
| `EventSourcedWorkflowActor` | 工作流身份、执行生命周期、Journal、恢复入口 | 将传输批次进度与已确认的目标提交分开；表达协调中、阻塞和失败原因 |
| `WorkflowExecutionEngine` | 逐批等待、取消、错误归属、Source/Sink 抽象 | 把重放判定交给稳定身份协议；Source ACK 必须服从完整提交证据 |
| `MySQLCdcSourceNode` | 真实 Debezium、完整 offset、Schema 身份校验 | 不再把回调序号当作事件身份；补充可验证的源事件位置与阶段信息 |
| `MySQLCdcApplySinkNode` | 目标 DML 与去重证据同事务、冲突拒绝 | 支持重分批下的事件覆盖判断；提交结果可被恢复协调读取 |
| 批次桥接 | 有界队列、确认句柄、关闭释放 | 共享捕获域时协调多个下游完成状态，不能任意越过慢表 |
| 测试设施 | 真 MySQL、真 Journal、强制退出、审计、全表对账 | 扩展窗口矩阵，持续保留失败证据 |

已有的 Schema 身份检查和账本冲突检查都值得保留。它们让不受支持的情况显式失败。新协议要提供安全的继续路径，不能只删除这些检查来获得绿色日志。

## 2. 先把协议适用范围收窄

第一阶段只处理：单活捕获者、固定 Schema、已有主键、streaming 阶段、源日志仍可读取、单个事务型 MySQL 目标。源事件必须按规定顺序进入同一个目标分区；目标去重证据与业务写入同事务提交。

这些假设有实际含义。没有单活约束，旧进程可能在新进程之后覆盖数据；Schema 改变后，相同字段序列不一定具有相同含义；日志已清理时，旧 D 不一定还能重放；初始快照重跑则可能读取一个新的数据库视图。这些情况不能靠“事件去重”四个字统一处理。

第一阶段也不承诺源事务跨表、跨批次在目标端整体原子可见。当前实验中一个 64 行 UPDATE 被分成多个目标批次，已经说明源事务与目标事务边界可能不同。若业务要求事务级可见性，需要单独设计事务缓冲、提交协调及大事务资源上限。

## 3. 分开传输身份、事件身份和提交身份

建议引入三个概念，名称只是设计说明，不是已有 API：

**deliveryToken** 标识本次回调，用来关联内存资源、日志和确认句柄。进程重启或批次变化后允许改变。

**eventId** 标识一个可重放的业务事件。同一源事件不应因回调分组不同而改变，不同源事件不能错误合并。它不能仅使用表主键，因为同一行会被修改多次；也不能直接拿整批末尾的 offset 作为每一行的身份。

**commitSeq / commitToken** 标识目标确认过的提交证据。它用于 Actor 协调目标事实，而不要求等于 Debezium 第几次回调。若恢复后一批混有已提交和新事件，结果必须能表达本次所覆盖的事件集合或连续范围。

eventId 的候选输入可以包括源谱系、日志事件位置、事件内行序号、操作分量与快照 generation，但这还不是已经证明可用的公式。必须从真实 SourceRecord 中验证这些值的稳定性和唯一性：同一 binlog event 的多行更新，主键更新拆出的删除与插入，事务内多次修改同一主键，以及恢复后的重读都不能产生歧义。主库切换时的谱系识别也需要单独约定。

**批次哈希只适合校验“这次传输内容有没有变”，不能替代跨重新分批的事件身份。** payload 摘要可以用于发现同 eventId 内容冲突，但规范化规则必须包含 Schema 语义；发现冲突应阻塞并报警，不能任选一个覆盖。

## 4. 用不变量约束恢复过程

在上述假设成立时，可以先定义下面四条验收不变量：

1. **目标原子性。** 对每个事件 e，它的持久去重证据与本次目标业务效果在同一事务中提交或回滚。
2. **身份稳定性。** 同一源事件在不同回调分组中保持同一个 eventId；不同事件不能共享身份。相同身份且 payload 不同必须被检测为冲突。
3. **确认有据。** J 中的每一个确认都能关联到 T 中已经持久提交的证据。T 先于 J 是允许的；J 不得把尚无目标证据的事件宣告完成。
4. **源进度不跳过缺口。** 允许推进 D 的前提，是该进度之前所有应处理事件都已有可恢复的处理证据。多分区、多表场景要定义覆盖集合或连续前缀，不能只取最大的完成序号。

第四条使用的是恢复语义，不能实现为对 JSON 中 pos 字段求最大值。它还依赖 Source 的过滤、事务和恢复规则：并非每个原始记录都对应一条目标 DML，但每个被确认的记录都必须有清晰归宿。

由此得到一个候选恢复流程：

```text
恢复 J 中的执行身份与阶段
  → 校验源身份、Schema 与所有权
  → 读取 T 中可证明的提交事实，协调 J 的缺口
  → 从 D 启动 Source 重放
  → 对重放中的已提交事件去重，新事件正常提交
  → 持久化对应 J 确认
  → 在覆盖条件满足后确认 Source，观测 D 落盘
```

这里的 T 是目标提交事实的依据，不是可以任意拿来覆盖 D 的新 offset。直接把 T 最大位置写回 Debezium store，可能跳过尚未完成的事件或破坏事务内恢复上下文。第一阶段应保持 Debezium 正常重放，用稳定身份消化重复，再在后续研究中评估有证明的恢复加速。

## 5. 重分批不再改变业务含义，但证明仍有条件

设原提交集合为 `{e1,…,e16}`。恢复首批只有 e1，新协议查到 e1 的目标提交证据，因此不重复写业务数据；随后 e2 到 e16 也能独立判定。反过来，如果恢复首批包含 e1 到 e20，就跳过已提交的前 16 个，在同一目标事务规则下提交其余事件。

这个推演依赖每个事件身份正确、目标去重证据可靠、同分区顺序受控。它只说明分批变化不应影响“是否已经应用”的判断，不能自动推出任意并发、任意旧 Checkpoint 或多目标原子提交的正确性。

事件账本还会付出存储与索引成本。如果每个事件都持久记录，长期高吞吐会放大写入和清理压力。可以研究连续范围压缩，但必须先证明顺序和空洞规则；不能先删逐事件证据，再假定一个最大值代表全部完成。

去重账本的清理边界也不能只看“D 最近已经前进”。如果仍允许恢复到更老的 Checkpoint，或者旧 owner 还可能写入，被清理的事件仍会再次出现。清理必须与允许的最老恢复点、源日志保留、旧 owner 失效和审计要求共同约束。

## 6. 海量表共享读取器，会把单表协议变成多路协调

假设共享日志先后产生 A 表的 a1 和 B 表的 b1。B 的 writer 很快，A 因 Schema 问题停住。如果按 b1 的位置推进共享 D，崩溃后 a1 可能无法重读。

有两条可以研究的路径：保持源确认停在 a1 之前，让整个捕获域承受背压；或者先把 a1 可靠写入独立的可重放存储，再允许源前进。后一条增加了新的持久边界和消费进度，不能继续用三份状态的简单图隐藏它。

这也是为什么不应在当前恢复协议未厘清时直接扩到 70 万张表。共享 Engine 可以降低连接开销，却会扩大慢表的影响范围，并引入跨表完成前缀。分组策略需要在资源成本与隔离成本之间做选择。

同样，Cluster Sharding 管理 Actor 的归属，不会自动使旧进程失去对 MySQL 的写权限。多节点阶段需要 ownership epoch 或其他 fencing 机制，并让目标提交与共享源状态写入都拒绝旧 owner。当前 Engine 的同 executionId 取消只在本进程内协调，不能当作跨进程 fencing。

## 7. 快照与 DDL 必须单独建模

当前 [`MySQLSnapshotSourceNode`](https://github.com/Xuxiaotuan/pekko-reference/blob/d88ec80f2a7166cfdaddf1284cc268a68bc62e28/pekko-server/src/main/scala/cn/xuyinyin/magic/workflow/nodes/sources/MySQLSnapshotSourceNode.scala)使用最大主键边界与 keyset 分页。它提供有界读取的进度，不包含完整的 LOW/HIGH 回填与跨 Chunk 协调协议。另一个 `mysql.cdc` 节点启动的是 Debezium initial snapshot，不能把两条路径混成项目自有的并行增量快照。

若将来实现分片快照，需要明确 split 范围、LOW/HIGH、扫描结果与日志合并、已完成分片、全局切换条件及故障后的 generation。主键跨分片迁移尤其不能用“原主键已扫过”推导“新位置一定会出现”。验收需要固定迁移、水位和故障时序的真实 Reader 与完整作业实验，不能移植前一组 Flink 文章的结果当作本项目通过。

Schema 也不能只依赖 Debezium history。当前 Source 配置 `include.schema.changes=false`，重启时校验初始列身份；这与端到端 DDL 演进协议不同。后续至少需要为数据关联 Schema 版本，定义旧版本缓冲何时排空、目标 DDL 如何幂等、何时持久记录切换完成。DDL 已完成但 J 未记录的恢复窗口，与 DML 提交窗口有相似结构，却未必具有相同事务能力。

## 8. 故障矩阵决定是否可以进入下一阶段

| 场景 | 固定的方法 | 必须保留的判定证据 | 当前状态 |
|---|---|---|---|
| T 后、J 前，同批重放 | 提交后闸门，强制退出 | T/J/D、审计、全量字段差异 | 原协议已测成功 |
| T 后、J 前，拆批 | 真实 Debezium 16→1 | 完整事件、批次身份、cursor、Actor 终态 | 原协议已测失败；新协议未实现 |
| T 后、J 前，合批 | 真实小批提交后以更大批恢复 | 已提交/新事件混合去重，无覆盖缺口 | 未验证 |
| J 后、D 前 | 固定持久化后、offset 刷盘前窗口 | 真实 J 已前进、D 仍旧、重读身份 | 未验证 |
| COMMIT 成功、回复丢失 | 在事务返回边界断连或终止 | 独立 SQL 证明提交，恢复不重复业务效果 | 未验证 |
| 同位置多行、主键变化 | 固定真实事务与 binlog 记录 | eventId 稳定且不碰撞，删除/插入配对正确 | 未验证 |
| 接管后旧 owner 恢复 | 两进程固定网络与写入时序 | 旧 epoch 的目标和 offset 写入均被拒绝 | 未验证 |
| 快照期间迁移键 | 固定 split、LOW/HIGH、迁移点 | 全量对账及恢复前后分片状态 | 未验证 |
| 旧 Schema 数据未排空时 DDL | writer 闸门与版本切换 | 旧数据不被新 Schema 误解码，DDL 重试可判定 | 未验证 |

每个场景都要保留运行终态与数据终态。目标拒绝冲突是安全性证据的一部分，但作业长期 failed 仍不满足可用性；全表最终相等也不能单独证明没有中间重复副作用，因此必须保留事务审计。

下一次代码改造应先解决已复现的身份问题，并补测相邻的 J/D 窗口。等固定 Schema、单活 streaming 的协议有了端到端证据，再扩大到共享捕获、快照、Schema 与集群接管。这样的顺序让每一步增加的能力，都有一个可以独立失败、独立解释的验收条件。
